# 프로젝트 법률·약관 가드 (Project Legal Guard)

데이터 분석 프로젝트는 **시작할 때 한 번 확인하고 잊어버리기** 쉽다. 그런데 문제는 중간에 생긴다. 새 데이터셋을 붙이거나, 외부 API나 LLM에 데이터를 보내거나, 결과를 공개하는 순간에 위법 소지가 생긴다. 이 스킬은 두 가지를 한다.

1. **시작 시 조사**: 프로젝트에 적용되는 법령과 데이터 출처 약관을 실제로 찾아 읽고, 위반 소지를 점검한다.
2. **지속 상기**: 결과를 `COMPLIANCE.md`에 남기고 `CLAUDE.md`에 연결해, 이후 모든 세션과 작업에서 해당 조항이 기준이 되게 한다.

**중요한 한계**: 이 스킬은 법률 자문이 아니다. 법령은 개정되고 해석은 사안마다 다르다. 위험도가 높거나 애매하면 "변호사·개인정보 담당자 확인 필요"로 분류해 사용자에게 알린다. 단정적으로 "합법"이라고 말하지 않는다. 문제 없음이 아니라 "확인된 범위에서 위반 소지를 발견하지 못함"이라고 쓴다.

## 먼저 확인: 이미 컴플라이언스 체계가 있는가

프로젝트에 `COMPLIANCE.md`(또는 `docs/COMPLIANCE.md`), CLAUDE.md의 준수 규칙, 상기용 훅이 이미 있으면 **재점검 모드**로 진행한다. 사용자가 공들여 만든 체계를 덮어쓰면 안 되기 때문이다.
- 기존 파일을 수정하지 않고 읽기만 해서, 이미 충족된 것(🟢)과 빠진 것(🟡/🔴)을 비교해 보고한다.
- 변경은 사용자가 승인한 항목만 반영한다. CLAUDE.md 블록·훅이 이미 있으면 중복해서 넣지 않는다.

## 1단계: 프로젝트 파악

사용자 설명과 프로젝트 파일을 보고 아래를 정리한다. 모르는 항목은 한 번에 묶어서 짧게 묻되, 핵심(어떤 데이터를 어디서 가져와 무엇을 하는가)을 알 수 있으면 가정하고 진행한 뒤 가정을 명시한다.

- **데이터 출처**: 직접 수집(설문·로그), 크롤링/스크래핑, 공공데이터, 유료/제3자 데이터셋, 외부 API, 사내 데이터
- **데이터 종류**: 개인정보 여부(이름·연락처·ID·IP·위치·영상·건강·금융 등), 가명·익명 처리 여부, 민감정보·고유식별정보 포함 여부
- **정보주체/지역**: 한국인만인지, 해외(EU, 미국 캘리포니아 등) 이용자 데이터가 섞이는지
- **처리 방식**: 어디에 저장하나(국내/해외 클라우드), 외부 서비스(LLM API, 분석 SaaS)로 데이터를 보내는가
- **산출물**: 내부 보고용인가, 외부 공개·판매·논문·서비스 적용인가
- **목적**: 수집 당시 고지된 목적과 지금의 분석 목적이 같은가

## 2단계: 적용 법령·약관 조사

기억에 의존하지 말고 **현행 원문을 확인**한다. 법 조문 번호와 내용은 개정되기 때문이다. 웹 검색·페치 도구가 있으면 `law.go.kr`(국가법령정보센터)과 해당 서비스의 약관·robots.txt·API 정책 페이지를 직접 읽는다. 도구가 없거나 페이지가 스크립트 기반이라 본문이 안 읽히면(law.go.kr에서 흔하다), 법제처 법령 검색 결과·개인정보보호위원회 사이트·국가법령정보 공동활용 API 같은 대체 경로를 시도하고, 그래도 안 되면 그 사실을 밝히고 "조사 못 한 항목"으로 남긴다. 확인 못 한 조문을 인용해 판단 근거로 쓰지 않는다.

1. `references/korea-law-map.md`를 읽어 프로젝트 특성에 해당하는 한국 법령 후보를 추린다. (이 파일은 출발점일 뿐, 조문은 원문으로 재확인한다.)
2. **해외 데이터·이용자가 있으면** 해당 국가 법도 같은 방식으로 조사한다. (예: EU 이용자 → GDPR, 캘리포니아 → CCPA/CPRA, 중국 → PIPL.) 한국 법과 달라지는 핵심(법적 근거, 국외이전, 정보주체 권리)을 짚는다.
3. **데이터 출처별 약관**을 확인한다: 이용약관의 크롤링·재배포·상업적 이용·AI 학습 조항, API 호출 제한과 저장 기간 제한, 데이터셋 라이선스(CC BY, CC BY-NC, 공공누리 유형 등), robots.txt.
4. 각 항목에 **근거**(법령명·조문 또는 약관 URL·확인 날짜)를 남긴다. 근거 없는 판단은 쓰지 않는다. 추측이면 추측이라고 쓴다.

**공개 데이터라도 결합 시 재식별 위험을 따진다.** 컬럼에 이름·ID가 없어도 시각(초 단위)·장소(주거지 인근)·희귀 조합이 겹치면 특정인의 패턴이 드러날 수 있다. 준식별자(시간, 장소, 기기 번호)를 찾고, 집계 결과에서 건수가 너무 적은 셀을 합치거나 숨기는 기준(소수 셀 임계값)을 규칙으로 정한다.

## 3단계: 점검 결과 정리

각 쟁점을 다음으로 분류한다.

- 🔴 **위반 가능성 높음 / 중단·변경 필요**: 예) 동의 없이 개인정보 수집, 약관이 금지하는 크롤링 강행
- 🟡 **조건부 / 확인 필요**: 가명처리, 동의 확보, 라이선스 확인 등 조치를 하면 가능한 경우, 또는 법률 전문가 확인이 필요한 경우
- 🟢 **확인된 범위에서 문제 없음**: 근거와 함께

🔴가 있으면 작업을 이어가기 전에 사용자에게 먼저 알리고 대안(익명화, 공개 데이터로 대체, 동의 확보, 수집 범위 축소)을 제시한다.

## 4단계: COMPLIANCE.md 작성과 CLAUDE.md 연결

1. 프로젝트 루트에 `COMPLIANCE.md`를 만든다. `assets/COMPLIANCE-template.md` 구조를 따른다. 핵심은 **"지켜야 할 규칙"을 짧은 행동 규칙으로 요약한 섹션**이다. 법 조문 설명이 길면 매 세션 읽히는 효과가 약해지므로, 규칙은 "~하지 않는다 / ~할 때는 ~한다" 형태의 한 줄씩으로 쓰고 상세 근거는 아래 표에 둔다.
2. 프로젝트 `CLAUDE.md`(없으면 생성)에 아래 블록을 추가한다. 이미 있으면 중복해서 넣지 않고 갱신한다. 사용자의 기존 CLAUDE.md 내용은 건드리지 않는다.

```markdown
## 법률·약관 준수 (필독)
이 프로젝트는 `COMPLIANCE.md`의 규칙을 따른다. 아래 상황에서는 작업 전에 해당 파일을 확인하고, 규칙에 걸리면 진행 전에 사용자에게 알린다.
- 새 데이터 소스를 추가·수집·크롤링할 때
- 데이터를 외부 서비스(API, LLM, 클라우드)로 보낼 때
- 데이터셋을 합치거나 개인을 식별·추적할 수 있는 분석을 할 때
- 결과·데이터를 공유, 공개, 배포, 판매할 때
- 보관 기간이 지났거나 수집 목적이 달라질 때
```

3. 사용자에게 `COMPLIANCE.md`의 위치, 🔴/🟡 항목, 사용자가 직접 확인해야 할 사항을 알린다. 파일을 만들거나 CLAUDE.md를 수정한 사실을 숨기지 않는다.

## 5단계: 프로젝트 진행 중 상기

`COMPLIANCE.md`가 있는 프로젝트에서 작업할 때는 다음을 지킨다.

- 4단계 CLAUDE.md의 트리거 상황이 오면 **작업 전에** 관련 규칙을 한 줄로 상기시킨다. 길게 설교하지 않는다. 예: "이 CSV에는 전화번호 컬럼이 있습니다. COMPLIANCE.md 규칙 3에 따라 가명처리 후 분석합니다."
- 규칙과 충돌하는 요청이면 실행하기 전에 멈추고 충돌 내용·근거·대안을 알린다. 사용자가 감수하겠다고 해도 위험은 기록(COMPLIANCE.md의 결정 기록)에 남긴다.
- 데이터·목적·범위가 바뀌면 해당 부분만 재조사하고 `COMPLIANCE.md`를 갱신한다. 갱신 날짜를 남긴다.
- 코드에서 개인정보 컬럼을 출력·로깅·커밋하려 할 때, 원본 데이터를 저장소에 올리려 할 때(`.gitignore` 점검)도 상기한다.

## 하지 말아야 할 것

- 법령 조문을 기억만으로 인용하지 않는다. 확인하지 못했으면 "미확인"으로 표시한다.
- 근거 없이 "합법입니다", "문제없습니다"라고 말하지 않는다.
- 과도한 경고로 모든 작업을 막지 않는다. 프로젝트와 무관한 법까지 나열하지 말고, 해당되는 것만 다룬다.
- 사용자의 실제 개인정보 값을 COMPLIANCE.md나 대화에 옮겨 적지 않는다. 컬럼명과 유형만 쓴다.
