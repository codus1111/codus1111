## 빠졌거나 보강하면 좋은 것 (🟡)

1. **재식별 가능성 판단이 문서에 없음**
   - CSV 컬럼: 자전거번호, 대여·반납 일시(초 단위), 대여·반납 대여소ID·명·좌표·주소 등 (이용자 ID·성별·연령은 없음).
   - 단독으로는 이용자를 알아보기 어렵지만, **아파트 단지 대여소 + 심야/새벽 시간 + 초 단위 시각**은 특정 거주자의 이동 패턴을 추정할 여지가 있다. 개인정보보호법상 "다른 정보와 쉽게 결합하여 알아볼 수 있는" 정보인지(제2조 제1호 계열)는 제공기관이 공개 데이터로 낸 것이라도 **결합 분석 시 따로 판단**해야 한다.
   - COMPLIANCE §2에 "집계 단위로만 공개"는 있지만, **소수 셀 억제 기준**(예: 한 셀의 건수가 n 미만이면 합치거나 숨김)은 없다.
   - 제안 규칙: "집계 결과에서 건수 10 미만 셀은 공개하지 않거나 합산한다(임계값은 사용자가 정함)."

2. **자전거번호 단위 분석의 경계가 모호함**
   - 규칙 4는 "자전거번호 단위의 개별 경로 추적 금지"인데, 재배치 연구에서 자전거별 순환을 볼 필요가 생길 수 있다. 자전거번호는 이용자가 아니라 기기 식별자라는 점을 근거로 허용 범위를 명시하면 훅이 불필요하게 막지 않는다. (결정은 사용자 몫)

3. **에이전트 단계에서 LLM API로 데이터 전송 (아직 미착수지만 `.env.example`에 ANTHROPIC_API_KEY 있음)**
   - 에이전트가 원자료 행을 API로 보내면 외부 서비스 전송이 된다. 규칙으로 "LLM에는 집계 결과와 대여소 단위 요약만 보낸다, 행 단위 원본은 보내지 않는다"를 미리 넣을 것.
   - 사용할 서비스(Anthropic API)의 데이터 보관·학습 사용 약관은 사용 시점에 재확인 필요 (오늘 미확인).

4. **외부 지도·위치 보강 데이터(학교·역·아파트 위치) 사용 시 라이선스**
   - 원인 규명 단계에서 위치 특성 데이터를 붙일 예정이다. 카카오·네이버 지도 API 결과의 저장·재가공은 약관 제한이 흔하다. 쓸 데이터를 정할 때 약관을 먼저 확인하도록 COMPLIANCE에 트리거를 추가.

5. **결과 공개 시 지도 시각화**
   - 대여소 단위 지도는 문제 없어 보이나, 아파트 대여소를 시간대별로 세분화해 올리면 1번과 같은 쟁점. 공개 전 점검 항목에 추가.

## 확인하지 못한 것 (조사 못 한 항목)
- **개인정보 보호법 조문 원문**: `law.go.kr` 페이지가 스크립트 기반이라 본문을 가져오지 못했다. 위 1번의 조문 인용은 **미확인**이며, 원문 확인 전에는 판단 근거로 확정하지 않는다.
- 대전교통공사/타슈 이용약관 원문(데이터 보유 근거로 인용된 것)과 개인정보 처리방침.
- 공공데이터법상 제공 데이터의 개인정보 비식별 처리 여부(제공기관 확인 필요).

## 스킬 개선점 (이번 테스트에서 발견)
- 이미 컴플라이언스 체계가 있는 프로젝트에서의 **재점검 모드**가 SKILL.md에 명시돼 있지 않다 → 기존 파일 덮어쓰기 금지, 차이만 보고, 변경은 사용자 승인 후 반영하도록 추가 필요.
- `law.go.kr`가 WebFetch로 안 읽힐 때의 대체 경로(국가법령정보 공동활용 API, 법제처 법령 검색 결과 페이지, 개인정보보호위원회 사이트) 안내 추가.
- 공개 데이터라도 **결합 시 재식별 위험**을 판단하는 항목을 체크리스트 템플릿에 추가 (소수 셀 임계값, 준식별자: 시간·장소).
- CLAUDE.md에 이미 훅이 있는 경우 CLAUDE.md 블록을 중복해서 넣지 않도록 확인.
