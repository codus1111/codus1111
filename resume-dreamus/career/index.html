AI 도구가 보조한 일Claude Code로 수집·정제·분석 코드, 에이전트, 웹 화면 구현

주요 수행 내용

  • 회사명 정규화로 사업장을 회사 단위로 정리하고, 사업자번호로 DART 기업과 연결: 2,678곳 중 2,617곳(97.7%) 매칭, 직원 수가 비슷한 상장사 2,392곳을 검증에 사용
  • 보정 모델 5개를 5겹 교차검증으로 비교. 복잡한 모델이 단순한 선형 모델보다 낫지 않아 데이터 규모에 맞는 단순한 모델 선택
  • Microsoft Clarity로 클릭·화면 이동을 녹화하고, 직접 받은 피드백과 함께 사용성 테스트 진행
  • 답마다 👍👎 "이 추정 도움이 됐나요?" 피드백을 받아 구글 시트로 모으는 구조 구현

문제 상황 및 해결 과정

가설·발견확인한 원인판단·해결

여러 달을 평균하면 더 정확오히려 14.7% → 17.6%로 악화. 기준소득월액이 매년 7월 전년도 소득으로 갱신돼 달마다 소득 연도가 다름소득 연도를 맞춰 비교(한 달·3개월 모두 14.6%) → 최신 한 달 자료 사용
“검색이 한 글자만 된다” (사용자 피드백)한글 조합 중 Enter를 누르면 마지막 글자로 다시 검색됨글자 조합이 끝난 뒤 한 번만 검색

타슈 공공자전거 수급 불균형 분석

진행기간 2026 · 개인 프로젝트 · 대전 공영자전거 공공데이터

801만 건SQL로 집계한 대여 기록
1,406곳분석한 대여소
2.13→1.62배날씨 통제 후 학기 효과
10건가설·실험 기록
개요
대전 공영자전거 타슈 대여 기록으로 대여소가 언제 비고 넘치는지 찾고, 재배치 우선순위를 질문으로 물어볼 수 있는 에이전트까지 제작어느 대여소가 어느 시간대에 반복해서 비거나 넘치는지, 왜 그런지(위치 특성, 날씨) 밝히기
데이터
대여 이력 2025.12 ~ 2026.10, 8,008,537건·대여소 1,406곳(공공데이터포털), 시간별 날씨(Open-Meteo)
사용 기술
SQL(DuckDB)PythonnumpyGemini APIClaude Code

담당 역할

직접 한 일분석 질문과 가설 설정, 데이터 약관 확인, 결과 해석과 한계 정리, 에이전트 답변 검토
AI 도구가 보조한 일Claude Code로 집계 스크립트, 대시보드, 질의응답 에이전트 구현

주요 수행 내용

  • 대여 기록을 SQL(DuckDB)로 대여소·시간대별 집계. 월별 파일의 인코딩이 섞여 있어(UTF-8/CP949) 파일마다 감지해 읽음
  • 평일 출근 시간 아파트 단지 대여소는 7~9시 순유출 -45~-64%, 퇴근 시간 연구단지·KAIST는 -27~-84%로 반복 불균형 확인
  • 날씨·요일 영향 측정: 비 1mm 이상 0.36배, 5°C 미만 0.32배, 주말 0.64배
  • 가설 → 실험 → 결과 → 오류 분석 형식으로 실험 10건 기록, 결과를 대시보드로 정리
  • 집계 결과만 조회하는 도구로 답하는 재배치 질의응답 에이전트 제작

문제 상황 및 해결 과정

가설·발견확인한 내용판단·해결
학기 중 수요 증가는 날씨 때문에 부풀려진 것 아닐까날씨를 통제하자 학기 효과가 2.13배 → 1.62배계절 착시가 약 1/4임을 확인하고 결론에 반영
대여소 단위 시간당 수요를 예측할 수 있을까캠퍼스 전체는 기준선보다 3% 개선, 대여소 단위는 거의 예측 못 함안 된 결과도 그대로 기록하고 반복 패턴 목록 중심으로 전환
에이전트 자동 점검은 통과했지만 답이 좋은가직접 읽어 보니 눈을 비로 가정하고 밝히지 않은 답, 근거 없는 조언 발견찾은 문제를 점검 항목으로 추가 → 가정 밝힘 12/12, 근거 없는 조언 0
쿠키런·유튜브 댓글 분석을 먼저 검토개발자 정책의 파생 데이터 금지·저장 제한과 충돌 가능주제를 이용 제한 없는 공공데이터(타슈)로 변경

“부족”은 순유출로 추정한 압력이며 실제 고갈과 다릅니다. 대전교통공사·대전광역시와 제휴 관계가 없는 개인 학습 프로젝트입니다.

문제 상황 및 해결 과정

피드백·발견원인판단·해결

“튜토리얼 1분은 길다”안내가 7단계4단계(약 30초)로 줄이고, 원하는 사람만 보는 선택형으로
“어렵다”대기 시간·주문 간격·주문 개수가 빡빡함예전 값과 쉬운 값의 중간으로 조정
자동 플레이 결과에서 러시 점수가 전체의 90%러시가 거의 끝나지 않는 버그고친 뒤 러시가 제시간에 끝나는 것을 확인하고, 영향받은 랭킹 초기화

특정 패스트푸드 브랜드와 무관한 개인 프로젝트입니다. 그림과 소리는 모두 코드로 만들었습니다.

주요 수행 내용

  • 고객 응대 및 주문 접수: 고객의 요청과 상황에 맞춰 대응
  • POS 및 키오스크 운영: 키오스크가 정상적으로 작동하지 않을 때 POS로 주문을 받아 처리
  • 메뉴 및 상품 판매 관리: 본사에서 등록한 신메뉴·상품을 판매 시작일에 맞춰 POS에서 판매 상태로 변경
  • 제품 제조 및 매장 운영
  • 고객 요청 및 현장 문제 대응: 품절·판매 종료 메뉴 주문 등 현장에서 생긴 문제 처리
  • 동료와의 업무 분담 및 협업

문제 상황과 대응

상황고객에게 생긴 불편대응
키오스크 작동 오류주문을 할 수 없음POS로 주문을 받아 주문이 끊기지 않게 처리
품절·판매 종료 메뉴가 키오스크에 그대로 남음주문한 메뉴를 받을 수 없음고객에게 사과하고 환불 처리

배운 점

  • 메뉴 정보가 채널마다 늦게 반영되면 그 불편은 결국 고객이 겪는다는 것을 현장에서 확인했습니다.
  • 이 경험이 이후 프로젝트 햄부기 러시의 기획 출발점이 됐습니다.
